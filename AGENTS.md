# AGENTS.md

This file provides guidance to coding agents when working with code in this repository.

## What this is

`@tomowang/dsh-tui` is an out-of-tree terminal front door for [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) (`dsh`). It stacks on `@deepseek-ai/dsh-base` the same way `dsh-web-app`/`dsh-headless` do, but drives the agent from a TTY instead of a browser. It is simultaneously:

- a **Cordis plugin** (`src/index.ts`, name `tui`) that owns terminal input/presentation only — agent lifecycle, session persistence, tool execution, and model policy stay in `dsh-base`;
- a **dsh bundle** (`package.json`'s `dsh.bundle.patch` points at `cordis.patch.yml`) that inserts `tui-startup` and `tui` into the plugin tree and disables `hmr` (module-reload redraws would fight the interactive terminal).

The terminal layer (`src/tui/`) is built on [`@earendil-works/pi-tui`](https://www.npmjs.com/package/@earendil-works/pi-tui), a standalone differential-rendering TUI library — not React/Ink. There is no JSX anywhere in this repo (every file under `src/tui/` is plain `.ts`); components are plain classes implementing pi-tui's `Component` interface (`render(width): string[]`, `invalidate()`, an optional `handleInput(data)`), mutated directly rather than re-rendered from props.

## Commands

```sh
pnpm install
pnpm run build        # tsc -p tsconfig.json → lib/
pnpm run typecheck     # tsc --noEmit
pnpm run lint          # eslint .
pnpm run test          # vitest run
```

A Husky `pre-push` hook (`.husky/pre-push`, wired via the `prepare` script) runs lint, typecheck, test, and build before every push, so failures surface locally instead of in CI. To exercise the TUI end-to-end, point a `dsh` profile's dependency at this checkout and rebuild before each run — profiles load the built `lib/` under plain Node, not `src/`:

```sh
dsh plugin --profile tui add /path/to/dsh-tui
pnpm run build
dsh --profile tui
dsh --profile tui --resume <sessionId>
dsh --profile tui --dump-config   # inspect the composed plugin tree
```

Both stdin and stdout must be real TTYs — `apply()` in `src/index.ts` throws loudly otherwise instead of degrading, so pipes/CI must use `dsh --profile headless`.

## Keep docs in sync

Before committing a feature (new/changed command, keybinding, overlay, or user-visible behavior), check whether `README.md` and this file describe the old behavior and update them in the same commit — not as a follow-up. `README.md` covers user-facing surface (Features, the terminal-commands/keyboard-shortcuts tables); this file's `## Architecture` and `## Current status / roadmap` cover implementation notes and the known-gaps list. A shipped feature still listed as a "known gap" here, or a new `/command`/shortcut missing from README's tables, counts as an incomplete change.

## Commit scopes

Every commit uses a [Conventional Commits](https://www.conventionalcommits.org/) `type(scope): subject`, drawn from this closed list — pick the one covering the primary area touched (a commit spanning several picks the most significant one, not a comma-joined list):

| Scope | Covers |
|---|---|
| `tui` | `src/tui/**` (components, overlays, the store, the prompt editor, theme), `src/render.ts`, `src/markdown.ts` — the terminal UI and the session-log-to-terminal formatting it renders |
| `plugin` | `src/index.ts` — Cordis plugin lifecycle, session/agent wiring, in-terminal approval/question answerers |
| `startup` | `src/startup.ts`, `cordis.patch.yml` — CLI flag parsing and the bundle's plugin-tree patch |
| `release` | Versioning, `CHANGELOG.md`, `cliff.toml`, the npm-publish workflow |
| `deps` | Dependency-only changes not tied to a feature/fix |
| `ci` | GitHub Actions workflows other than the release one |
| `repo` | Repo-wide contributor/process docs not about one code area (e.g. this scope table) |

A docs-only commit still scopes to the subject it documents (`docs(tui): …` for a README/AGENTS.md update about the terminal UI), not a generic catch-all. `git-cliff` groups the changelog by `type` (see `cliff.toml`'s `commit_parsers`), not `scope`, so scope is for readability/`git log --grep`, not changelog sectioning.

## Architecture

**Two-plugin split (`src/startup.ts` → `src/index.ts`).** `tui-startup` parses this app's CLI flags (everything after the launcher's own args) via `dsh-cmdline`/commander and publishes them as an ordinary Cordis service (`TUI_STARTUP_SERVICE` / `tuiStartup`). The `tui` plugin injects that service rather than parsing argv itself — this mirrors how `dsh-headless` is structured and keeps startup-value resolution lazy/testable. The wiring between the two is declared in `cordis.patch.yml`, not in code.

**Log-first rendering.** The TUI never holds its own mutable view of "what happened" — it renders only from the durable, append-only `agent.session.events` log (`src/render.ts`). On startup it replays persisted events, then follows live `session/event` emissions through the same formatting path (`formatEvent` in `render.ts`). This is what makes `--resume` show exactly the history the log carries, and replay and live events render identically: `user/message` prints on both paths, so a submitted prompt stays visible in the transcript once the prompt box clears it. A `user/message`'s `source.kind` also decides how much of it shows: `'user'` (a direct human prompt) prints in full, while `'plugin'` (synthetic `agent.inject()` context — subdir AGENTS.md, skill content, cron notices, …) collapses to one label line instead of dumping its content, mirroring how a web chat UI collapses injected-context rows.

**Store as the seq-dedupe boundary (`src/tui/store.ts`).** `TuiStore` is a dependency-free, framework-agnostic projection — a plain class with `getSnapshot()`/`subscribe()`, not coupled to pi-tui or Cordis. It owns the one invariant that keeps replay and live event streams from double-rendering: `appendEvent` drops anything with `seq <= lastSeq`. Session/agent event listeners in `index.ts`'s `run()` all funnel into this store; components never touch Cordis events directly, and never touch each other's state — every component (live-region row, overlay) reads straight from `store.getSnapshot()` at render/input time rather than being handed a snapshot as a prop, so there's no manual state-pushing to keep in sync.

**Store → UI bridge (`src/tui/TuiApp.ts`).** `TuiApp` is the one place that turns store changes into screen changes, and it uses two different strategies deliberately. The live region (notice, queued preview, streaming text, pending-tool-call spinner row, status bar, stats line, permission indicator) is a `DynamicText`/`Spinner` per row (`src/tui/text.ts`), each pulling straight from `store.getSnapshot()` inside its own `render()` — there is no manual `setText` bookkeeping, every repaint just reflects whatever the store currently holds. The transcript is append-only instead: `appendNewTranscriptItems` diffs the store's `events`/`shellHistory` arrays against how much has already become a `PreStyledText` child of the transcript's `Container`, appending only the new tail — re-formatting the whole transcript on every store change would be wasteful for a long session, and pi-tui's `ScrollView` (wrapping that `Container`, `follow: 'end'` to auto-scroll) paints only the visible viewport regardless of how many children it holds.

**Input routing (`src/index.ts` `actions.send`).** Line input maps to the agent inbox based on current status: `agent.followup()` while idle, `agent.steer()` while a turn is running. `Ctrl+C` cancels the running turn while one is active; idle behavior (clear text, then two-press-to-exit) and the rest of the app-level key handling (Ctrl+O, shift+tab, `!` shell mode) are intercepted at the top of `CustomEditor.handleInput` (`src/tui/CustomEditor.ts`) before falling through to `super.handleInput` for everything pi-tui's `Editor` already implements — see the note below.

**Model-profile services are optional, re-checked at point of use.** `settings`, `credentials`, and `llm` are *not* in this plugin's `inject` array (only `agentDefaultModel`, `agents`, `sessions` are required) because not every profile mounts them. The `/model` overlay (`src/tui/modelProfile/`) degrades to an error notice instead of refusing to start the whole TUI when they're absent — see `requireModelProfileServices()` in `index.ts`, which every model-profile action call re-checks rather than caching.

**Custom provider persistence.** User-declared LLM providers are joined at read time from `ctx.llm.listConfigurableProviders()` (static/live catalog) against `ctx.settings.describe()` (persisted overrides) and `ctx.credentials.describe()` (API key presence, redacted). Writes go through `settings.mutate()` with an explicit `revision` for optimistic-concurrency, and a *new* custom provider is namespaced under `CUSTOM_PROVIDER_NAMESPACE` (`llm-pi-ai`) with its route as the settings path segment. `deriveApiKeyRef()` turns a route like `my-proxy` into a POSIX credential ref `MY_PROXY_API_KEY`.

**Rendering entry point (`src/tui/TuiApp.ts`).** `mountTui()` is the only place that constructs a `TuiAltScreen` and builds the component tree: a `ScrollView`-wrapped transcript `Container` on top, a `dock` `VStack` (notice, queued preview, streaming text, pending-tool-call spinner row, status bar, the prompt editor, permission indicator, stats line) pinned below it via `setLayoutRoot`'s flex sizing (`basis: 0, grow: 1` for the transcript; `basis: 'auto'` for the dock) — no manual row-counting math to keep the two from overflowing the terminal, unlike a native-scrollback model would need. Overlays (`/model`, `/trajectory`, Ctrl+O tool cards, `/context`, `/plugins`, `/presets`, approval, question) are `tui.showOverlay(component, options)` calls keyed off `store.getSnapshot().overlay.kind` in `TuiApp.updateOverlay` — each is its own small class under `src/tui/*/`, shown as a full-width panel anchored at the top of the screen.

**The prompt editor subclasses pi-tui's `Editor` rather than hand-rolling readline (`src/tui/CustomEditor.ts`).** Multi-line motion, kill-ring word ops, undo, and history recall are Editor defaults — pi-tui's default keybindings already match this app's conventions almost 1:1 (Ctrl+B/F, Ctrl+A/E, Alt+Left/Right, Ctrl+W, Alt+D, Ctrl+K/U all come for free; `TuiApp.ensureKeybindings()` only adds the Ctrl+P/Ctrl+N Emacs aliases and wires history recall onto up/down). `CustomEditor.handleInput` intercepts only what Editor has no equivalent for — Ctrl+O (Tool Cards), shift+tab (permission-preset cycle), `!` shell mode, and the two-press Ctrl+C/Ctrl+D exit-arm sequence — short-circuiting before `super.handleInput` so Editor's own bindings never see those keys. Slash-command and `@`-mention completion are a `PromptAutocompleteProvider` (`src/tui/promptAutocomplete.ts`) wrapping this app's own `commands.ts`/`fileMention.ts`/`fileIndex.ts` query logic (kept in place rather than switching to pi-tui's built-in `fd`-shelling file completion) and wired via `editor.setAutocompleteProvider` — Editor renders and drives that dropdown itself.

**In-terminal approval/question answerers.** `src/index.ts`'s `run()` registers two Cordis-context-scoped (not per-session) answerers behind a single shared FIFO queue (`interactionQueue`/`activeInteraction`), so an approval and a multi-question `ask_user_question` call never fight over the one overlay slot: a bare `ctx.on('approval/request', …)` listener answers `@deepseek-ai/dsh-user-approval`'s tool-approval waterfall (`ApprovalOverlay`, y/n/allow-reject), and `ctx.userQuestions.registerProvider(...)` (optional — only when that profile mounts it) answers `@deepseek-ai/dsh-user-questions`' seam behind `ask_user_question` and `dsh-plan-mode`'s `exit_plan_mode` plan review (`QuestionOverlay`, option cursor + multi-select + free-text "Other…" via the hand-rolled `miniTextField` helper, `esc` to skip a question). Both route through whichever session's `store` is current, so a `/clear` mid-request still lands the prompt on the live screen; see `src/tui/interaction/`.

**Shell mode bypasses the agent loop entirely (`src/tui/CustomEditor.ts`, `store.ts`).** A leading `!` typed at an empty prompt — Claude Code's convention — flips a local `shellMode` flag on `CustomEditor`, which swaps Enter's meaning to "run this line as a local shell command" instead of `agent.followup()`/`agent.steer()`. The command runs outside the agent loop and never touches `agent.session.events`; its output is a display-only transcript entry that `TuiStore` interleaves with real session events in completion order, so it settles into the transcript alongside agent output without being persisted or replayed on `--resume`. `Esc` or backspace on an empty shell-mode buffer exits back to normal mode.

**`@`-file-mention is prompt-text insertion, not a wire-format change (`src/tui/fileMention.ts`, `fileIndex.ts`).** `mentionQuery()` detects an open `@token` ending at the cursor (whitespace-delimited, so it can open mid-sentence); `matchFileCandidates()` fuzzy-ranks the repo's file index (`git ls-files`, falling back to a bounded walk outside a git repo) by path-prefix, then basename-prefix, then length. `Tab`/`Enter` splices the picked path into the prompt buffer at the `@` — the model only ever sees a plain path string and reads the file itself once the prompt is sent, mirroring the `/`-slash-command dropdown's shape.

**Markdown rendering is detect-then-style, not a parser (`src/markdown.ts`).** `renderMarkdown()` is applied to both settled `assistant/message` text and the live streaming fold (`formatStreamingText`, both in `src/render.ts`), and is a no-op unless `looksLikeMarkdown()` first finds an unambiguous signal (fenced code, ATX header, list, blockquote, rule, table row, link, bold, strikethrough, or inline code) — plain prose, including text with a stray `*`/`_`, passes through byte-for-byte unchanged so this never mangles ordinary chat replies. Detection deliberately excludes lone single-`*`/`_` emphasis on its own (highest false-positive risk: globs, multiplication, snake_case) — it only renders once some other cue has already confirmed the text is Markdown. Rendering itself is a line-oriented pass with a small fenced-code state machine, not a CommonMark-conformant parser, so multi-line inline spans and nested block constructs (e.g. a header inside a blockquote) aren't specially handled — reasonable for terminal chat output, not a general-purpose renderer. Table rows are detected (to avoid misfiring the plain-prose path) but not box-drawn.

**Reasoning content renders as a distinct violet block ahead of the visible text.** `reasoningOf()` mirrors `textOf()` but keeps `type === 'reasoning'` blocks instead (`src/render.ts`); both settled `assistant/message` rendering and the live streaming fold (`formatStreamingText`, called from the streaming-text `DynamicText` row in `TuiApp.ts`) call both extractors and, when reasoning is non-empty, prefix it with a dim `✦ thinking` label rendered in `theme.reasoning` — set apart from the assistant's answer rather than interleaved with it. `TuiStore.foldChunk` folds `reasoning-delta` chunks into `StreamingState.reasoningText` the same way `text-delta` chunks fold into `.text`, using the same `BlockAssembler` instance so ordering across interleaved block indexes stays correct.

**Tool calls are collapsed by default; a spinner stands in for the pending state, not a card.** A `tool/call` event never gets its own transcript line — `formatEvent`'s `'tool/call'` case always returns `undefined` (`src/render.ts`). While a call has no matching `tool/result` yet, it's carried in `TuiStore.pendingToolCalls` (an insertion-ordered map of `callId -> {name, arguments}`, pruned by `callId` when the result lands — see `store.ts`'s `appendEvent`) and rendered as a spinner line per call in the live region (`formatPendingToolCalls`, a `DynamicText` in `TuiApp.ts` next to `streamingText`), using the shared status-bar `Spinner`'s current frame. Once the `tool/result` event appends, `formatEvent`'s `'tool/result'` case renders exactly one collapsed transcript line — `formatToolCardSummary`'s `icon + title` — rather than the full multi-line card; the pending row for that call simply stops being pending on the next store snapshot; there is no separate "settle" step to coordinate. Full, uncapped card detail (for either half of the pair) is still only available in the Tool Cards overlay: `Ctrl+O` or `/tools` (`src/tui/toolCards/ToolCardsOverlay.ts`) pairs each `tool/call` with its `tool/result` by `callId` into one `ToolCardRow` (`cards()`) — so the overlay's item count matches the transcript's collapsed-line count, not the raw event count — and the selected row renders through `formatToolCardDetail` for each half present (blank-line separated when both are, `detailOf()`) instead of the transcript's collapsed line; a still-pending call (no result yet) is a row of its own, and an orphaned result with no call in the log (e.g. truncation) gets a trailing row too. `rowKey()` (the call's `seq`, falling back to the result's) keeps `expanded`/scroll state stable across a row's pending→resolved transition, since `cards()` rebuilds the row list fresh on every render. Expanded detail can be scrolled (`↑↓`/`PageUp`/`PageDown`/`Home`/`End`) once opened (`Enter`/`Space`) — its own hand-rolled scroll-offset math (not pi-tui's `ScrollView`, since a `showOverlay` panel isn't part of the constrained `VStack`/`ScrollView` layout tree) reads the live terminal height off `tui.terminal.rows` each render so it adapts to a resize. `MAX_CARD_LINES` in `src/render.ts` no longer bounds tool cards at all — it's only the shell-escape (`!`) run cap now (`formatShellRun`/`formatShellRunLive`).

**`/trajectory` ledger rows carry a kind tag, mirroring the web portal.** `TrajectoryLedger.ts`/`layout.ts` color-tag each row USER/CONTEXT/ASSISTANT/TOOL/HEADER, splitting the former single `'user'` record kind into `'user'` (a direct human prompt) and `'context'` (plugin-injected AGENTS.md, skill content, cron notices, …) by the underlying event's `source.kind` — the same split `formatEvent` already makes for transcript rendering. Only a `'user'` row's full text reaches the ledger's Payload tab; a `'context'` row stays collapsed there too, so nothing leaks the full injected-context payload into the inspector. An assistant row with no visible text but non-empty reasoning shows a reasoning preview instead of falling straight to "(tool calls only)".

## Current status / roadmap

Functionally a complete single-session terminal client — session replay/resume, streaming, tool cards with an expand/collapse overlay, in-terminal approvals/questions, model/preset/compaction/permission management, shell mode, `@`-file-mention autocomplete, persisted prompt history, and full-screen differential rendering are all in place. The TUI runs in the terminal's alternate screen buffer (pi-tui's `TuiAltScreen`) with an application-owned, mouse/trackpad/keyboard-scrollable transcript viewport (`follow: 'end'` auto-scroll to the bottom while the reader hasn't manually scrolled up) and a `VStack`-pinned live region (status bar and boxed prompt) below it — see the "Rendering entry point" architecture note above. The tradeoff that comes with owning the viewport: native terminal scrollback copy/paste of history is gone in exchange; `/trajectory` is the full-history browser for anything scrolled out of the transcript's window, and `tui stop()` flattens the final transcript into plain scrollback on exit so the last screenful is still copyable afterward. Assistant text streams live from `assistant/chunk` (folded via `@deepseek-ai/dsh-llm`'s `BlockAssembler` in `TuiStore`, rendered in the live region until the step settles — see `src/tui/store.ts`). A pending tool call shows as a single spinner line in the live region until its `tool/result` lands, then settles into one collapsed `✓`/`✖` transcript line — the title from a tool's declared `presentCall`/`presentResult` (`@deepseek-ai/dsh-tools`) when available, falling back to the flat tool name/arguments otherwise (see `formatEvent`/`formatPendingToolCalls` in `src/render.ts`); `Ctrl+O`/`/tools` opens the Tool Cards overlay for the full presentation behind any collapsed line — a diff, a terminal block, grouped search matches, a line-numbered read, web citations (see the architecture note above). Approvals and model questions (`ask_user_question`, plan-mode review) are answered in-terminal — see the "In-terminal approval/question answerers" architecture note above. `restoreActiveTerminal()` (`src/tui/TuiApp.ts`) is registered on `process.once('exit', ...)` once the TTY check passes, and synchronously calls `tui.stop()` (raw mode, alt-screen exit, cursor visibility) as a last line of defense against a SIGTERM, an early SIGINT, or an uncaught exception leaving the reader's shell in raw mode inside the alternate screen.

## Releasing

Changelog and GitHub Release notes are generated from [Conventional Commits](https://www.conventionalcommits.org/) via [git-cliff](https://git-cliff.org/) (`cliff.toml`). To cut a release:

1. Bump `version` in `package.json` (e.g. `npm version --no-git-tag-version <patch|minor|major>`).
2. `pnpm run changelog` — regenerates `CHANGELOG.md`, folding commits since the last tag into a new `vX.Y.Z` section.
3. Review the diff, then `git add package.json CHANGELOG.md && git commit -m "chore(release): vX.Y.Z"`.
4. `git tag vX.Y.Z && git push && git push --tags`.

Pushing the tag triggers `.github/workflows/release.yml`, which re-verifies the build, checks the tag matches `package.json`'s version, cuts a GitHub Release from `CHANGELOG.md`'s latest section, and publishes to npm via [Trusted Publishing](https://docs.npmjs.com/trusted-publishers/) (OIDC — no stored npm token). One-time setup: on the `@tomowang/dsh-tui` package's npmjs.com settings, add a Trusted Publisher pointing at this GitHub repo with workflow filename `release.yml`.
