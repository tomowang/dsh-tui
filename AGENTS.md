# AGENTS.md

This file provides guidance to coding agents when working with code in this repository.

## What this is

`@tomowang/dsh-tui` is an out-of-tree terminal front door for [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) (`dsh`). It stacks on `@deepseek-ai/dsh-base` the same way `dsh-web-app`/`dsh-headless` do, but drives the agent from a TTY instead of a browser. It is simultaneously:

- a **Cordis plugin** (`src/index.ts`, name `tui`) that owns terminal input/presentation only — agent lifecycle, session persistence, tool execution, and model policy stay in `dsh-base`;
- a **dsh bundle** (`package.json`'s `dsh.bundle.patch` points at `cordis.patch.yml`) that inserts `tui-startup` and `tui` into the plugin tree and disables `hmr` (module-reload redraws would fight the interactive terminal).

The terminal layer (`src/tui/`) is built on [`@earendil-works/pi-tui`](https://www.npmjs.com/package/@earendil-works/pi-tui), a standalone differential-rendering TUI library — not React/Ink. There is no JSX anywhere in this repo (every file under `src/tui/` is plain `.ts`); components are plain classes implementing pi-tui's `Component` interface (`render(width): string[]`, `invalidate()`, an optional `handleInput(data)`), mutated directly rather than re-rendered from props.

## Commands

```sh
pnpm install
pnpm run build        # tsc -p tsconfig.json → lib/
pnpm run typecheck     # tsc --noEmit
pnpm run lint          # eslint .
pnpm run test          # vitest run
```

A Husky `pre-push` hook (`.husky/pre-push`, wired via the `prepare` script) runs lint, typecheck, test, and build before every push, so failures surface locally instead of in CI. To exercise the TUI end-to-end, point a `dsh` profile's dependency at this checkout and rebuild before each run — profiles load the built `lib/` under plain Node, not `src/`:

```sh
dsh plugin --profile tui add /path/to/dsh-tui
pnpm run build
dsh --profile tui
dsh --profile tui --resume <sessionId>
dsh --profile tui --dump-config   # inspect the composed plugin tree
```

Both stdin and stdout must be real TTYs — `apply()` in `src/index.ts` throws loudly otherwise instead of degrading, so pipes/CI must use `dsh --profile headless`.

## Keep docs in sync

Before committing a feature (new/changed command, keybinding, overlay, or user-visible behavior), check whether `README.md` and this file describe the old behavior and update them in the same commit — not as a follow-up. `README.md` covers user-facing surface (Features, the terminal-commands/keyboard-shortcuts tables); this file's `## Architecture` and `## Current status / roadmap` cover implementation notes and the known-gaps list. A shipped feature still listed as a "known gap" here, or a new `/command`/shortcut missing from README's tables, counts as an incomplete change.

## Commit scopes

Every commit uses a [Conventional Commits](https://www.conventionalcommits.org/) `type(scope): subject`, drawn from this closed list — pick the one covering the primary area touched (a commit spanning several picks the most significant one, not a comma-joined list):

| Scope | Covers |
|---|---|
| `tui` | `src/tui/**` (components, overlays, the store, the prompt editor, theme), `src/render.ts`, `src/markdown.ts` — the terminal UI and the session-log-to-terminal formatting it renders |
| `plugin` | `src/index.ts` — Cordis plugin lifecycle, session/agent wiring, in-terminal approval/question answerers |
| `startup` | `src/startup.ts`, `cordis.patch.yml` — CLI flag parsing and the bundle's plugin-tree patch |
| `release` | Versioning, `CHANGELOG.md`, `cliff.toml`, the npm-publish workflow |
| `deps` | Dependency-only changes not tied to a feature/fix |
| `ci` | GitHub Actions workflows other than the release one |
| `repo` | Repo-wide contributor/process docs not about one code area (e.g. this scope table) |

A docs-only commit still scopes to the subject it documents (`docs(tui): …` for a README/AGENTS.md update about the terminal UI), not a generic catch-all. `git-cliff` groups the changelog by `type` (see `cliff.toml`'s `commit_parsers`), not `scope`, so scope is for readability/`git log --grep`, not changelog sectioning.

## Architecture

**Two-plugin split (`src/startup.ts` → `src/index.ts`).** `tui-startup` parses this app's CLI flags (everything after the launcher's own args) via `dsh-cmdline`/commander and publishes them as an ordinary Cordis service (`TUI_STARTUP_SERVICE` / `tuiStartup`). The `tui` plugin injects that service rather than parsing argv itself — this mirrors how `dsh-headless` is structured and keeps startup-value resolution lazy/testable. The wiring between the two is declared in `cordis.patch.yml`, not in code.

**Log-first rendering.** The TUI never holds its own mutable view of "what happened" — it renders only from the durable, append-only `agent.session.events` log (`src/render.ts`). On startup it replays persisted events, then follows live `session/event` emissions through the same formatting path (`formatEvent` in `render.ts`). This is what makes `--resume` show exactly the history the log carries, and replay and live events render identically: `user/message` prints on both paths, so a submitted prompt stays visible in the transcript once the prompt box clears it. A `user/message`'s `source.kind` also decides how much of it shows: `'user'` (a direct human prompt) prints in full, while `'plugin'` (synthetic `agent.inject()` context — subdir AGENTS.md, skill content, cron notices, …) collapses to one label line instead of dumping its content, mirroring how a web chat UI collapses injected-context rows.

**Store as the seq-dedupe boundary (`src/tui/store.ts`).** `TuiStore` is a dependency-free, framework-agnostic projection — a plain class with `getSnapshot()`/`subscribe()`, not coupled to pi-tui or Cordis. It owns the one invariant that keeps replay and live event streams from double-rendering: `appendEvent` drops anything with `seq <= lastSeq`. Session/agent event listeners in `index.ts`'s `run()` all funnel into this store; components never touch Cordis events directly, and never touch each other's state — every component (live-region row, overlay) reads straight from `store.getSnapshot()` at render/input time rather than being handed a snapshot as a prop, so there's no manual state-pushing to keep in sync.

**Store → UI bridge (`src/tui/TuiApp.ts`).** `TuiApp` is the one place that turns store changes into screen changes, and it uses two different strategies deliberately. The live region (notice, goal strip, queued preview, streaming text, pending-tool-call spinner row, status bar, stats line, permission indicator, update hint) is a `DynamicText`/`Spinner` per row (`src/tui/text.ts`), each pulling straight from `store.getSnapshot()` inside its own `render()` — there is no manual `setText` bookkeeping, every repaint just reflects whatever the store currently holds. The transcript is append-only instead: `appendNewTranscriptItems` diffs the store's `events`/`shellHistory` arrays against how much has already become a `PreStyledText` child of the transcript's `Container`, appending only the new tail — re-formatting the whole transcript on every store change would be wasteful for a long session, and pi-tui's `ScrollView` (wrapping that `Container`, `follow: 'end'` to auto-scroll) paints only the visible viewport regardless of how many children it holds.

**Input routing (`src/index.ts` `actions.send`).** Line input maps to the agent inbox based on current status: `agent.followup()` while idle, `agent.steer()` while a turn is running. `Ctrl+C` cancels the running turn while one is active; idle behavior (clear text, then two-press-to-exit) and the rest of the app-level key handling (Ctrl+O, shift+tab, `!` shell mode) are intercepted at the top of `CustomEditor.handleInput` (`src/tui/CustomEditor.ts`) before falling through to `super.handleInput` for everything pi-tui's `Editor` already implements — see the note below.

**Model-profile services are optional, re-checked at point of use.** `settings`, `credentials`, and `llm` are *not* in this plugin's `inject` array (only `agentDefaultModel`, `agents`, `sessions` are required) because not every profile mounts them. The `/model` overlay (`src/tui/modelProfile/`) degrades to an error notice instead of refusing to start the whole TUI when they're absent — see `requireModelProfileServices()` in `index.ts`, which every model-profile action call re-checks rather than caching.

**Custom provider persistence.** User-declared LLM providers are joined at read time from `ctx.llm.listConfigurableProviders()` (static/live catalog) against `ctx.settings.describe()` (persisted overrides) and `ctx.credentials.describe()` (API key presence, redacted). Writes go through `settings.mutate()` with an explicit `revision` for optimistic-concurrency, and a *new* custom provider is namespaced under `CUSTOM_PROVIDER_NAMESPACE` (`llm-pi-ai`) with its route as the settings path segment. `deriveApiKeyRef()` turns a route like `my-proxy` into a POSIX credential ref `MY_PROXY_API_KEY`.

**Rendering entry point (`src/tui/TuiApp.ts`).** `mountTui()` is the only place that constructs a `TuiAltScreen` and builds the component tree: a `ScrollView`-wrapped transcript `Container` on top, a `dock` `VStack` (notice, goal strip, queued preview, streaming text, pending-tool-call spinner row, status bar, the approve/reject panel, the prompt editor, permission indicator, update hint, stats line) pinned below it via `setLayoutRoot`'s flex sizing (`basis: 0, grow: 1` for the transcript; `basis: 'auto'` for the dock) — no manual row-counting math to keep the two from overflowing the terminal, unlike a native-scrollback model would need. Overlays (`/model`, `/trajectory`, Ctrl+O tool cards, `/context`, `/plugins`, `/presets`, question) are `tui.showOverlay(component, options)` calls keyed off `store.getSnapshot().overlay.kind` in `TuiApp.updateOverlay` — each is its own small class under `src/tui/*/`, shown as a full-width panel anchored at the top of the screen. Approval is the one exception: `updateOverlay` special-cases `overlay.kind === 'approval'` to skip `showOverlay` entirely, instead handing the `ApprovalOverlay` instance to `ApprovalSlot` — a dock row that delegates render/input to it — and calling `tui.setFocus(approvalSlot)`, so the approve/reject panel shows inline in the live region (above the prompt editor) without covering the transcript; the editor stays visible, just unfocused, until the decision settles and focus returns to it.

**The prompt editor subclasses pi-tui's `Editor` rather than hand-rolling readline (`src/tui/CustomEditor.ts`).** Multi-line motion, kill-ring word ops, undo, and history recall are Editor defaults — pi-tui's default keybindings already match this app's conventions almost 1:1 (Ctrl+B/F, Ctrl+A/E, Alt+Left/Right, Ctrl+W, Alt+D, Ctrl+K/U all come for free; `TuiApp.ensureKeybindings()` only adds the Ctrl+P/Ctrl+N Emacs aliases and wires history recall onto up/down). `CustomEditor.handleInput` intercepts only what Editor has no equivalent for — Ctrl+O (Tool Cards), shift+tab (permission-preset cycle), `!` shell mode, and the two-press Ctrl+C/Ctrl+D exit-arm sequence — short-circuiting before `super.handleInput` so Editor's own bindings never see those keys. Slash-command and `@`-mention completion are a `PromptAutocompleteProvider` (`src/tui/promptAutocomplete.ts`) wrapping this app's own `commands.ts`/`fileMention.ts`/`fileIndex.ts` query logic (kept in place rather than switching to pi-tui's built-in `fd`-shelling file completion) and wired via `editor.setAutocompleteProvider` — Editor renders and drives that dropdown itself.

**In-terminal approval/question answerers.** `src/index.ts`'s `run()` registers two Cordis-context-scoped (not per-session) answerers behind a single shared FIFO queue (`interactionQueue`/`activeInteraction`), so an approval and a multi-question `ask_user_question` call never fight over the one overlay slot: a bare `ctx.on('approval/request', …)` listener answers `@deepseek-ai/dsh-user-approval`'s tool-approval waterfall (`ApprovalOverlay`, y/n/allow-reject), and `ctx.userQuestions.registerProvider(...)` (optional — only when that profile mounts it) answers `@deepseek-ai/dsh-user-questions`' seam behind `ask_user_question` and `dsh-plan-mode`'s `exit_plan_mode` plan review (`QuestionOverlay`, option cursor + multi-select + free-text "Other…" via the hand-rolled `miniTextField` helper, `esc` to skip a question). Both route through whichever session's `store` is current, so a `/clear` mid-request still lands the prompt on the live screen; see `src/tui/interaction/`.

**An OSC 9 desktop notification fires once per wait, not once per interaction.** `TuiApp.updateOverlay` (`src/tui/TuiApp.ts`) already gates on `overlay.kind` actually changing; the notification reuses that same transition — when the new kind is `'approval'` or `'userQuestion'` and the previous kind was neither, it writes `\x1b]9;<message>\x07` (`ESC ] 9 ; Pt BEL`, the same mechanism Claude Code's own CLI uses) via `tui.terminal.write`, with a message naming which kind of wait it is. That guard is what keeps a multi-question `ask_user_question` call (each answered question re-opens `'userQuestion'` with new content but the same kind) or a queued follow-up approval (`showNextInteraction` re-opening `'approval'` straight from `'approval'`) from re-firing — the reader is already looking at the prompt. No config flag and no OS-notifier dependency: terminals that understand OSC 9 (Ghostty, Kitty, iTerm2 with "Send escape sequence-generated alerts" enabled) forward it straight to the OS notification center when unfocused; a terminal without OSC 9 support just ignores the unrecognized sequence — this plugin only ever emits the byte, matching the same `\x1b]0;…` style already used for the window-title OSC 0 write above.

**`/plan` is the one command needing free-text arguments, so it bypasses the exact-match `SLASH_COMMANDS` dispatch.** Every other row in `commands.ts`'s `SLASH_COMMANDS` is a bare command word with no argument, matched by `matchSlashCommands()`'s whitespace-free prefix check and dispatched through `runSlashCommand`'s exhaustive switch. `/plan [message]`/`/plan off` can't fit that shape, so `commands.ts` also exports `parsePlanCommand()` — it recognizes `/plan` followed by end-of-line or whitespace and returns everything after it, trimmed — which `CustomEditor.handleSubmit` checks ahead of the whitespace-free path (`runSlashCommand` has no `/plan` case; it's unreachable through that switch on purpose). The parsed text becomes `actions.plan(rawInput)` in `index.ts`, mirroring `@deepseek-ai/dsh-plan-mode`'s own command handler against the optional `ctx.planMode` service (same re-checked-at-use pattern as `ctx.compaction`'s `/compact`): the exact argument `off` calls `planMode.set(agent, false)`, anything else calls `planMode.set(agent, true)` and, when the argument is non-empty, steers it as the first message under plan mode via `agent.steer()` — reusing the handler's own result wording as the notice line.

**Goal mode is a surface-only port: the domain already rides in via `dsh-base`.** The TUI bundle adds no `cordis.patch.yml` row — `@deepseek-ai/dsh-goal`'s `GoalService` (`ctx.goals`), `goal-round-driver` (automatic continuation at idle), `command-goal` (whose `ctx.commands` handler is unreachable from this prompt), and `tool-goal` (the `create_goal`/`get_goal`/`update_goal` agent tools) are all base rows the TUI profile already composes. What the TUI adds is the surface. `/goal` shares `/plan`'s parse-ahead shape (`src/tui/commands.ts`): `parseGoalCommand()` recognizes `/goal` followed by end-of-line or whitespace and returns the full `GoalCommand` union (`show`/`create`/`edit`/`invalid-edit`/`pause`/`resume`/`clear`), mirroring `command-goal`'s own parser — bare `edit` is an error, `edit <objective>` rewrites the objective, anything else is a create objective — and `CustomEditor.handleSubmit` checks it ahead of the whitespace-free path. The parsed command becomes `actions.goal(command)` in `index.ts`, mirroring `command-goal`'s handler against the optional `ctx.goals` service (re-checked at use, like `ctx.planMode`): a completed goal may be replaced by create or edit, every other current phase rejects create, and the handler's own result text (Status/Objective/Rounds/Activation/Commands hint) becomes the notice line. The goal strip (`buildGoalBarText` in `src/tui/liveText.ts`, a `DynamicText` dock row between the notice and the queued preview — the web portal's GoalBar sits above its Queue panel) reads `store.getSnapshot().goal`, the `goal` session projection seeded at attach from `sessionProjections.snapshot(session).values.goal` and refreshed on `sessionProjections.onChanged` with key `'goal'` (the same projection path as the stats line; `undefined` = unit not composed, `null` = absent/cleared). Mirroring the web GoalBar exactly, the strip shows glyph + phase label + truncated objective (blocked appends its reason — the terminal analog of the portal's hover tooltip) and renders nothing while loading, absent, or complete. In the transcript, `goal/change` events render one line per mutation (`formatEvent`, `src/render.ts`) — the web covers that trace with its `/goal` command-input chat node, which this prompt consumes without echoing — and an admitted continuation round (`user/message` with `source.kind === 'goal'`) collapses to a `⊕ goal › round N` label in `formatEvent`'s transcript rendering, and to a plain `goal · round N` label in the trajectory ledger's `userLabel` (`src/tui/trajectory/layout.ts`) — each surface keeps its own label style (the transcript's dim glyph-prefixed line vs. the ledger's plain-text row label) rather than sharing one literal string, matching the web's collapsed context rows while naming the round in both; the injected `<goal_round>` prompt stays folded in both.

**Shell mode bypasses the agent loop entirely (`src/tui/CustomEditor.ts`, `store.ts`).** A leading `!` typed at an empty prompt — Claude Code's convention — flips a local `shellMode` flag on `CustomEditor`, which swaps Enter's meaning to "run this line as a local shell command" instead of `agent.followup()`/`agent.steer()`. The command runs outside the agent loop and never touches `agent.session.events`; its output is a display-only transcript entry that `TuiStore` interleaves with real session events in completion order, so it settles into the transcript alongside agent output without being persisted or replayed on `--resume`. `Esc` or backspace on an empty shell-mode buffer exits back to normal mode.

**`@`-file-mention is prompt-text insertion, not a wire-format change (`src/tui/fileMention.ts`, `fileIndex.ts`).** `mentionQuery()` detects an open `@token` ending at the cursor (whitespace-delimited, so it can open mid-sentence); `matchFileCandidates()` fuzzy-ranks the repo's file index (`git ls-files`, falling back to a bounded walk outside a git repo) by path-prefix, then basename-prefix, then length. `Tab`/`Enter` splices the picked path into the prompt buffer at the `@` — the model only ever sees a plain path string and reads the file itself once the prompt is sent, mirroring the `/`-slash-command dropdown's shape.

**Markdown rendering is detect-then-style, not a parser (`src/markdown.ts`).** `renderMarkdown()` is applied to both settled `assistant/message` text and the live streaming fold (`formatStreamingText`, both in `src/render.ts`), and is a no-op unless `looksLikeMarkdown()` first finds an unambiguous signal (fenced code, ATX header, list, blockquote, rule, table row, link, bold, strikethrough, or inline code) — plain prose, including text with a stray `*`/`_`, passes through byte-for-byte unchanged so this never mangles ordinary chat replies. Detection deliberately excludes lone single-`*`/`_` emphasis on its own (highest false-positive risk: globs, multiplication, snake_case) — it only renders once some other cue has already confirmed the text is Markdown. Rendering itself is a line-oriented pass with a small fenced-code state machine, not a CommonMark-conformant parser, so multi-line inline spans and nested block constructs (e.g. a header inside a blockquote) aren't specially handled — reasonable for terminal chat output, not a general-purpose renderer. Table rows are detected (to avoid misfiring the plain-prose path) but not box-drawn.

**Reasoning content never dumps its raw body into the live region or transcript — an animated placeholder while it's in progress, a one-line summary once it settles.** `reasoningOf()` mirrors `textOf()` but keeps `type === 'reasoning'` blocks instead (`src/render.ts`); `TuiStore.foldChunk` folds `reasoning-delta` chunks into `StreamingState.reasoningText` the same way `text-delta` chunks fold into `.text`, using the same `BlockAssembler` instance so ordering across interleaved block indexes stays correct. The two rendering paths that read it are deliberately different functions, not one function parameterized by a mode: `formatStreamingText` (the streaming-text `DynamicText` row in `TuiApp.ts`, passed `this.spinner.current()` — the same braille frame the pending-tool-call row and status bar already animate from) renders a violet `spinnerChar thinking` line for as long as reasoning has started but no visible text has arrived yet, and switches to the plain rendered text the moment `text` becomes non-empty — the raw, fast-scrolling reasoning body itself is never printed live. `formatSettledMessage` (called from `formatEvent`'s `assistant/message` case, for the permanent transcript) instead prefixes the answer with `formatReasoningSummary`: a single dim-violet `✦ think · <80-char preview>` line via `truncate()`, never the full body. Neither path is a user-facing setting — there's no mode to switch, since collapsing noise is the only behavior. The complete reasoning text is always available regardless, via `/trajectory`'s per-record Preview/Raw tabs, which read the ledger row's `reasoning` field directly rather than through either of these renderers.

**Tool calls are collapsed by default; a spinner stands in for the pending state, not a card.** A `tool/call` event never gets its own transcript line — `formatEvent`'s `'tool/call'` case always returns `undefined` (`src/render.ts`). While a call has no matching `tool/result` yet, it's carried in `TuiStore.pendingToolCalls` (an insertion-ordered map of `callId -> {name, arguments}`, pruned by `callId` when the result lands — see `store.ts`'s `appendEvent`) and rendered as a spinner line per call in the live region (`formatPendingToolCalls`, a `DynamicText` in `TuiApp.ts` next to `streamingText`), using the shared status-bar `Spinner`'s current frame. Once the `tool/result` event appends, `formatEvent`'s `'tool/result'` case renders exactly one collapsed transcript line — `formatToolCardSummary`'s `icon + title` — rather than the full multi-line card; the pending row for that call simply stops being pending on the next store snapshot; there is no separate "settle" step to coordinate. Full, uncapped card detail (for either half of the pair) is still only available in the Tool Cards overlay: `Ctrl+O` or `/tools` (`src/tui/toolCards/ToolCardsOverlay.ts`) pairs each `tool/call` with its `tool/result` by `callId` into one `ToolCardRow` (`cards()`) — so the overlay's item count matches the transcript's collapsed-line count, not the raw event count — and the selected row renders through `formatToolCardDetail` for each half present (blank-line separated when both are, `detailOf()`) instead of the transcript's collapsed line; a still-pending call (no result yet) is a row of its own, and an orphaned result with no call in the log (e.g. truncation) gets a trailing row too. `rowKey()` (the call's `seq`, falling back to the result's) keeps `collapsed`/scroll state stable across a row's pending→resolved transition, since `cards()` rebuilds the row list fresh on every render. Every row renders expanded by default — `collapsed` is an opt-out set of rows the reader explicitly closed with `Enter`/`Space`, inverted from an "expanded" allowlist so a freshly-appended call/result pair needs no per-row toggle to read its full detail. Because every row can be open at once, `↑`/`↓` (and `Ctrl+P`/`Ctrl+N`) stay bound to moving the selection between cards regardless of the current row's open state — its old, closed-only meaning of "scroll" would otherwise make arrow-key browsing unreachable; scrolling a card's content lives on its own keys (`PageUp`/`PageDown`/`Home`/`End`) instead, with its own hand-rolled scroll-offset math (not pi-tui's `ScrollView`, since a `showOverlay` panel isn't part of the constrained `VStack`/`ScrollView` layout tree) that reads the live terminal height off `tui.terminal.rows` each render so it adapts to a resize. `MAX_CARD_LINES` in `src/render.ts` no longer bounds tool cards at all — it's only the shell-escape (`!`) run cap now (`formatShellRun`/`formatShellRunLive`).

**`/trajectory` ledger rows carry a kind tag, mirroring the web portal.** `TrajectoryLedger.ts`/`layout.ts` color-tag each row USER/CONTEXT/ASSISTANT/TOOL/HEADER, splitting the former single `'user'` record kind into `'user'` (a direct human prompt) and `'context'` (plugin-injected AGENTS.md, skill content, cron notices, …) by the underlying event's `source.kind` — the same split `formatEvent` already makes for transcript rendering. The collapsing is one-directional: the ledger's own one-line label/summary stays collapsed to the plugin/summary tag for a `'context'` row (`userLabel` in `layout.ts`), same as `formatEvent`'s transcript rendering, but its Preview/Raw/Source tabs — reached only by deliberately opening `/trajectory` and selecting the row — show the full injected content, mirroring the web ledger (`inputCellDetail` there sets `inputDetail` unconditionally for every `InputNode` kind, `'context'` included). An assistant row with no visible text but non-empty reasoning shows a reasoning preview instead of falling straight to "(tool calls only)".

**The detail pane's tab set is per-record-kind, ported from the web portal's `detailTabs()` (`TrajectoryTable.tsx`).** `detailTabsFor()` (`types.ts`) is the single source of truth that `TrajectoryOverlay` (`cycleTab`, and `render()`'s reset-to-`'summary'` guard when a stale tab from a differently-kinded record doesn't apply to the newly selected one) and `TrajectoryDetail.ts`'s tab-bar rendering both read from — a user/context/assistant record gets Summary/Preview/Raw, plus Source only when its event actually carried one (`user`/`context` always do, via `event.data.source`; `assistant` never does); a tool/header record gets Summary plus whichever of Payload/Result it actually has, and — tool only — Schema, always ending in Timing. `layout.ts` keeps a `TrajectoryRecord`'s `payload` (visible text) and `reasoning` (an assistant step's thinking) as two distinct fields, unlike the ledger row's one-line `label`/`summary` (which still folds one into the other for display) — so Preview/Raw can show both when present, mirroring the transcript's own reasoning-then-answer framing. `detail.ts`'s `schemaText()` resolves a tool record's Schema tab via `getTool(record.toolName)` — the live tool registry's current `{name, description, parameters}` (`ToolSchema`), not a per-request snapshot the way the web portal's `callSchemas` is, so it can drift from what an older call actually saw if the tool's declaration changed mid-session; `getTool` is plumbed into `TrajectoryOverlay`'s constructor the same optional, re-checked-at-use way it already reaches `ToolCardsOverlay`. `TrajectoryDetail.ts`'s `buildDetailLines` word-wraps that content to the pane's actual width via pi-tui's `wrapTextWithAnsi` before line-clamping to `detailContentHeight` — unlike a browser, the terminal won't soft-wrap a long unbroken paragraph or JSON line on its own, so `TrajectoryOverlay.render(width)` (previously an unused `_width`, since the ledger's own rows were always short enough not to need it) now threads the real pane width down to it. The panel reads visually distinct from the ledger above it via a blank line on each side (`TrajectoryOverlay.render`, its `heights()` chrome budget accounting for both) and a `DETAIL_INDENT` left margin on every body/placeholder/hidden-count line — mirroring the ledger's own flush-left "Turn" header / indented "Step" row convention (`TrajectoryLedger.ts`) — while the tab bar itself stays flush-left as the panel's heading. The right side gets an equal `DETAIL_RIGHT_PADDING` margin too, but purely by wrapping that much short of the pane's edge (`wrapWidth = width - DETAIL_INDENT.length - DETAIL_RIGHT_PADDING`) — there's no trailing character to place there the way the left indent has one to prepend.

**The update-check is a courtesy nudge, so every failure mode resolves to silence rather than an error.** `checkForUpdate()` (`src/updateCheck.ts`) fetches `@tomowang/dsh-tui`'s `latest` dist-tag from the public npm registry with a 2s `AbortController` timeout, and returns `undefined` — never throws — on a non-2xx response, a malformed body, a timeout, or any other network error; `isNewerVersion()` compares plain dotted-numeric parts (this repo only ever publishes `X.Y.Z`, per `## Releasing` below, so no semver pre-release/build-metadata handling is needed). `src/index.ts`'s `run()` fires this once per process (not re-run on `/clear`) right after the first `attachSession()`, and its `.then()` writes through the `current` closure variable rather than a captured store reference — the same "route through whichever session's store is current" pattern the approval/question answerers use (see above), so a `/clear` racing the still-in-flight fetch still lands the hint on the live session. `TuiStore.setUpdateHint()` holds the result in its own `updateHint` field rather than `notice`, since `notice` is cleared on the next input (`actions.send`) and this hint is meant to persist for the rest of the session; `buildUpdateHintText()` (`src/tui/liveText.ts`) renders it as a dock row (last, just above the stats line — see the "Store → UI bridge" note above) with the upgrade command (`dsh plugin --profile tui add @tomowang/dsh-tui`) baked into the line, and renders nothing while unchecked or already current.

**The terminal window/tab title rides in on the optional `dsh-session-title` service, the same "surface-only port" pattern as Goal mode.** `dsh-base`'s own bundle already composes `@deepseek-ai/dsh-session-title` (deterministic first-N-words fallback) and `@deepseek-ai/dsh-session-title-first-prompt-llm` (upgrades it to a short model-generated summary of the first user message, e.g. "Read-only agent preset creation" — the same source that fills the web portal's session-list nav rows), so the TUI bundle adds no `cordis.patch.yml` row for it — it just reads the `title` key (`string | null`, last-wins on the log-only `session/title` event) off the same `sessionProjections` registry `goal`/`stats` already read (`src/index.ts`'s `titleSnapshot`, seeded at `attachSession` and refreshed on `sessionProjections.onChanged` with key `'title'`; `undefined` = service not composed in this profile, `null` = no title accepted yet). `TuiStore.setTitle` holds it in its own `title` field. `TuiApp`'s `updateTerminalTitle` calls pi-tui's `Terminal.setTitle` (an OSC 0 escape) once at mount and again from the store-subscribe callback whenever `buildTerminalTitle()`'s formatted text (`src/tui/liveText.ts`) actually changes — `<session title> — dsh-tui` once one lands, else the bare `dsh-tui` fallback — deduped against `lastTerminalTitle` so an unrelated store change doesn't reissue the same write every render. Deliberately plain text, never ANSI-colored, since an OSC 0 title string is displayed verbatim by the terminal chrome rather than interpreted as SGR. A fresh `/clear` session gets a brand-new `TuiApp` (see the "Store as the seq-dedupe boundary" input-routing note above), so the title falls back to `dsh-tui` until the new session's own title lands, with no separate reset path needed.

**The docked subagent switcher deliberately isn't a `tui.showOverlay(...)` panel (`src/tui/TuiApp.ts`, `store.ts`, `index.ts`).** Every other overlay in this file (`/model`, `/trajectory`, Ctrl+O tool cards, …) is a full-width panel that takes over the whole screen and all input while it's open — right for a "different screen" the reader explicitly backs out of, wrong for watching a subagent while still wanting the composer and the strip itself live underneath. Viewing a child is instead `TuiState.viewingChild` (`ViewingChildState | undefined`), a plain top-level field outside the `Overlay` union entirely, which a new `TranscriptArea` component reacts to: `TuiApp` wraps `ScrollView` around `TranscriptArea` instead of `documentContainer` directly, and `TranscriptArea.render()` delegates to `documentContainer.render(width)` when nothing is being viewed, or renders the child's own transcript (`buildAgentDetailLines`, `src/tui/agents/detailLines.ts` — a per-log `tool/call` name/argument lookup plus `formatEvent`, the exact renderer the main transcript itself uses, word-wrapped and margined via the same `padTranscriptText` the other rebuilt-every-render live-region rows use) otherwise — `documentContainer` keeps accumulating the main session's history regardless of which one is currently on screen, so switching back always shows it caught up. `Left`/`Right` (`CustomEditor.handleInput`, gated on an empty prompt — neither key has a cursor to move at that point, so claiming them there takes nothing from normal editing) call `actions.cycleAgentsStrip(1 | -1)`, and `Escape` (same gating) calls `actions.closeAgentDetail()`; both are plain `CustomEditor` bindings, not an overlay's own `handleInput`, which is exactly what keeps the composer focused and responsive the whole time a child is being viewed.

**The strip (`buildAgentsStripText`/`agentsStripIsVisible`, `src/tui/liveText.ts`) is a live indicator of the current batch, not a permanent log, and `cycleAgentsStrip` (`src/index.ts`) must never navigate anywhere the strip didn't visibly offer.** `agentsStripIsVisible()` is the single predicate both read — visible while at least one child is `running`, or while a child's transcript is the one currently open (so the reader watching a child that finishes mid-view isn't stranded once nothing is `running` any more) — factored out specifically so the two can't drift apart the way they once did (`cycleAgentsStrip` used to allow navigating into a finished child from a past, fully-settled batch the strip itself would never have shown). With more than `AGENTS_STRIP_MAX_VISIBLE_CHILDREN` (4) children, `slidingWindow()` picks a window of that size biased toward the viewed index, recomputed fresh from it on every render rather than carried over as separate scroll-offset state, and a dim `‹N`/`N›` count marks whatever it excludes — `main` itself never scrolls out, only the child window does. The roster behind all of this (`TuiState.agentsStrip`) is kept live without polling or a dedicated child-lifecycle event, which the harness exposes none of: `refreshAgentsStrip` (a closure in `attachSession`) re-fetches `ctx.subagents.listChildren()` on the main session's own `tool/call`/`tool/result` events (spawning a subagent is a tool call) — a real cost on tool-heavy turns even when no subagent is involved, accepted as the simplest correct option over inventing a synthetic lifecycle signal — plus once on attach, for a `--resume`'d session that may already have children; `listChildren()`'s own oldest-first order is reversed so the strip reads latest-spawned first. `loadAgentDetail` (`src/index.ts`) reads a running child's live `Session` (`ctx.sessions.get`, the same in-process service `/resume` already depends on) or falls back to `ctx.sessionPersistence.inspect()` for a finished one; the fallback is awaited, so a later, faster `loadAgentDetail` call resolving before an earlier, slower one requires checking `store.getSnapshot().viewingChild?.childId` still matches before applying the result — otherwise a stale response can silently overwrite whichever transcript the reader has already cycled on to.

**A running child's circle also carries the shared status-bar `Spinner`'s current frame, deliberately kept independent of the solid/hollow selection marking (`buildAgentsStripText`, `src/tui/TuiApp.ts`).** Solid/hollow is purely a navigation signal ("what am I looking at"); the spinner is purely an activity signal ("what's still working") — conflating them into one glyph (e.g. a single "live" circle variant) would make "selected and running," "selected and finished," "unselected and running," and "unselected and finished" impossible to tell apart without four distinct glyphs, so the two stay orthogonal instead: every child's circle keeps its existing solid/hollow rule untouched, and `spinnerChar` (`buildAgentsStripText`'s third parameter) is appended right after it only when that specific child's own `activity === 'running'`, regardless of whether it's the one selected. The shared `Spinner` (`src/tui/Spinner.ts`) instance is reused rather than a second one — `TuiApp`'s own store-subscribe callback decides when to `start()`/`stop()` it, previously gated on `state.status === 'running'` (the main turn) alone; that gate is now `state.status === 'running' || state.agentsStrip.some(row => row.kind === 'child' && row.activity === 'running')`, since a subagent can still be running while the main agent sits idle (dispatched, then waiting) — without the widened gate the strip's spinner would freeze on a static frame exactly while a child is visibly still working.

## Current status / roadmap

Functionally a complete single-session terminal client — session replay/resume, streaming, tool cards with an expand/collapse overlay, in-terminal approvals/questions, model/preset/compaction/permission/plan-mode/goal management, the docked subagent switcher, shell mode, `@`-file-mention autocomplete, persisted prompt history, and full-screen differential rendering are all in place. The TUI runs in the terminal's alternate screen buffer (pi-tui's `TuiAltScreen`) with an application-owned, mouse/trackpad/keyboard-scrollable transcript viewport (`follow: 'end'` auto-scroll to the bottom while the reader hasn't manually scrolled up) and a `VStack`-pinned live region (status bar and boxed prompt) below it — see the "Rendering entry point" architecture note above. The tradeoff that comes with owning the viewport: native terminal scrollback copy/paste of history is gone in exchange; `/trajectory` is the full-history browser for anything scrolled out of the transcript's window, and `tui stop()` flattens the final transcript into plain scrollback on exit so the last screenful is still copyable afterward. Assistant text streams live from `assistant/chunk` (folded via `@deepseek-ai/dsh-llm`'s `BlockAssembler` in `TuiStore`, rendered in the live region until the step settles — see `src/tui/store.ts`). A pending tool call shows as a single spinner line in the live region until its `tool/result` lands, then settles into one collapsed `✓`/`✖` transcript line — the title from a tool's declared `presentCall`/`presentResult` (`@deepseek-ai/dsh-tools`) when available, falling back to the flat tool name/arguments otherwise (see `formatEvent`/`formatPendingToolCalls` in `src/render.ts`); `Ctrl+O`/`/tools` opens the Tool Cards overlay for the full presentation behind any collapsed line — a diff, a terminal block, grouped search matches, a line-numbered read, web citations (see the architecture note above). Approvals and model questions (`ask_user_question`, plan-mode review) are answered in-terminal — see the "In-terminal approval/question answerers" architecture note above. `restoreActiveTerminal()` (`src/tui/TuiApp.ts`) is registered on `process.once('exit', ...)` once the TTY check passes, and synchronously calls `tui.stop()` (raw mode, alt-screen exit, cursor visibility) as a last line of defense against a SIGTERM, an early SIGINT, or an uncaught exception leaving the reader's shell in raw mode inside the alternate screen.

## Releasing

Changelog and GitHub Release notes are generated from [Conventional Commits](https://www.conventionalcommits.org/) via [git-cliff](https://git-cliff.org/) (`cliff.toml`). To cut a release:

1. Bump `version` in `package.json` (e.g. `npm version --no-git-tag-version <patch|minor|major>`).
2. `pnpm run changelog` — regenerates `CHANGELOG.md`, folding commits since the last tag into a new `vX.Y.Z` section.
3. Review the diff, then `git add package.json CHANGELOG.md && git commit -m "chore(release): vX.Y.Z"`.
4. `git tag vX.Y.Z && git push && git push --tags`.

Pushing the tag triggers `.github/workflows/release.yml`, which re-verifies the build, checks the tag matches `package.json`'s version, cuts a GitHub Release from `CHANGELOG.md`'s latest section, and publishes to npm via [Trusted Publishing](https://docs.npmjs.com/trusted-publishers/) (OIDC — no stored npm token). One-time setup: on the `@tomowang/dsh-tui` package's npmjs.com settings, add a Trusted Publisher pointing at this GitHub repo with workflow filename `release.yml`.
